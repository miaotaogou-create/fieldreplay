# 多通道并发录放（E11）

- 状态：已确认（分阶段推进）
- 日期：2026-10-30
- 依据：MVP「配置若干通道并一键录制」；`.fcap` 已支持多通道表

## 背景

现场偶现问题常需 **同一时间轴上** 对照 UDP/TCP/串口/MQTT（乃至视频）才能定位。  
录制侧：E11a/b 已打通多路并发录制与 UI 一键启停；重放侧 E11c 控制面 `targets[]` + E11d UI 多目标一键重演已收口。  
`.fcap` 文件格式与会话载入 **已具备** 多通道表与按 `ch` 索引的帧。

## 目标模型

| 阶段 | ID | 内容 | 非目标 |
|------|-----|------|--------|
| E11a | 本阶段优先 | 一次会话内并发录制 ≥2 路；共享墙钟起点与相对时间轴；单 `.fcap`；控制面兼容旧单路；自检 | 录制中动态增删通道；跨进程多写者 |
| E11b | 随 E11a 或紧随 | UI：对全部 `enabled` 通道一键开始/停止录制；每路状态可见 | 录制中途改配置热更新 |
| E11c | 已完成 | 一次重放按时间轴 **对齐** 驱动多路目标（各通道独立 config）；倍速/暂停/seek/loop 作用于整会话 | 每通道独立倍速；跨会话合并；多路串口/TCP/MQTT/RTSP sink |
| E11d | 已完成 | UI：为会话内各通道配置重演目标并一键开重放 | 自动发现上位机端口 |

## 用户故事

1. 作为现场调试人员，我希望勾选多路通道后一键开始录制，以便一次出差带走相关链路的完整对照包。
2. 作为研发人员，我希望载入该包后多路按原相对时间灌回本机目标，以便复现「只在多链路交错时出现」的问题。
3. 作为既有脚本用户，我希望单路 `record.start` / CLI 行为不变，以便旧用法不破。

## 产品约定（已确认）

| 项 | 约定 |
|----|------|
| 时间基 | 整个会话 **一个** `start_wall_unix_us`；各通道帧共用相对微秒轴 |
| 通道表 | 在 `record.start`（多路）时一次性写入；本阶段 **不支持** 录制中途增删通道 |
| 启停 | 一次 start 启全部选定通道；一次 stop 停全部并 finalize |
| 启动失败 | 任一路在启动阶段打开失败 → 停掉已启各路，整次 start 失败（避免「残缺多通道」误导研判） |
| 运行中断连 | TCP 等按既有事件落盘；其余通道继续；不因此整会话失败 |
| 兼容 | 无 `channels` 数组时仍接受单路 `type`+`config`（等价于一路） |
| 重放匹配 | 按会话通道 **index** 绑定目标 config；缺目标的通道跳过并计入 `skipped`（须在响应/进度中可见） |
| 主交付 | 仍是 `.fcap`；与 E10 pcap 导出正交（多通道导出时规则不变：可导出 kind 进 pcap，串口/MQTT 跳过） |

## E11a 验收

- [x] 引擎可在同一 `SessionWriter` 上并发追加多通道帧（线程安全写盘；相对时间正确交错）
- [x] 控制面：`record.start` 支持 `channels:[{type,name?,config},…]`（≥2）；仍支持旧单路字段
- [x] `record.stop` 收尾一份含多通道表的 `.fcap`；`session` 载入后 `channels.length≥2`
- [x] 任一路启动失败：整次失败，无半开会话冒充成功
- [x] `self-check`：两路 UDP 环回并发录制 → 文件内两通道均有帧且时间轴同一会话
- [x] 单路路径行为与现网一致（回归）

## E11b 验收

- [x] UI 录制：开始时对所有 `enabled` 且引擎支持的通道下发多路 `record.start`（不再 `pickRecordChannel` 只取一路）
- [x] 界面可见每路类型/名称与汇总包计数；失败有可读错误
- [x] 未启用任何通道时开始录制有明确提示

## E11c 验收

- [x] 控制面：`replay.start` 支持 `targets:[{ch?,type,config},…]`（或等价结构）；按相对时间轴统一调度
- [x] 倍速 / 暂停 / seek / loop 作用于整次多路重放（共享同一 `ActiveReplay` 控制面）
- [x] 缺目标通道跳过并可观测（响应 `skipped[]`）；有目标通道载荷抽查与录制一致
- [x] `self-check`：两路 UDP 同会话对齐重放（`self_check_multi_udp_replay`）

已知限制（E11c）：多路 `targets[]` 本阶段仅打开 **UDP / 视频(UDP 推送)**；串口/TCP/MQTT/RTSP listen 请仍用单路 `type`+`config`，或待后续补 sink。

## E11d 验收

- [x] UI 重演：可为会话内各通道配置目标并一键开始（≥2 通道时下发 `targets[]`；单通道仍走协议页）
- [x] 进度与完成事件反映整会话（沿用 E11c 统一时间轴 `replay.progress` / `replay.done`；响应可见 `skipped[]`）

已知限制（同 E11c）：多路 UI 本阶段仅 UDP / 视频 UDP；串口/TCP/MQTT 在多通道会话中标为跳过。

## 非目标（本增强整轮）

- 录制暂停（单路也尚未做）
- 会话 trim / marker 标注 / 多文件 merge（可另立增强项）
- pcap → `.fcap` 导入
- MQTT 客户端证书（mTLS）
- 透明代理或旁路嗅探多网卡
- 修改 `.fcap` v1 布局（沿用现有多通道表）

## 风险与体验

- **端口冲突**：两路 UDP 绑同一端口应启动失败（整次失败），错误须可读。
- **性能**：多路高速率时写盘锁可能成瓶颈；先正确后测量，必要时再拆批量写（不提前上复杂无锁队列）。
- **心智**：UI 须避免「看起来配了多路、实际只录一路」的旧行为残留。
